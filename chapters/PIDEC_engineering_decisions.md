# Engineering Decisions

This section documents the load-bearing engineering decisions behind DrillGuard (EDIM), each with its trade-off and the alternative we rejected. Our governing constraints were: limited real labelled data, a single-student build window, and a §9.1 honesty obligation that forbids presenting unmeasured or simulated numbers as results. Every decision below optimises for *defensible, reproducible reliability* over surface impressiveness.

**1. Held-out-WELL evaluation, not a random split.**
The dominant practice in published drilling-ML papers is to pool all rows from all wells and split randomly into train/test. This leaks information: consecutive 10-second samples are autocorrelated, so a random split lets the model memorise a well's signature and report inflated metrics that collapse on a new rig. We instead train on a subset of wells and test on *wells the model has never seen* — the same generalisation challenge faced on a fresh well in the field. Trade-off: held-out-well scores are lower and noisier than random-split scores, which can look worse to a casual reader; we accept that because it is the only honest estimate of field performance. **Data constraint, stated plainly:** Volve provides only one usable well (31/5-7), so true cross-well validation is possible *only* on Bilabri's four wells (DEEP-1, D2, D3, D4); on Volve we are limited to a chronological time-segment holdout (train on early footage, test on later, never shuffling across the boundary). We disclose this asymmetry rather than implying cross-well validation everywhere.

**2. Interpretable baseline first (Isolation Forest / Random Forest), deep models second.**
We deliberately start with an unsupervised Isolation Forest anomaly baseline and a supervised Random Forest before any LSTM autoencoder. Rationale is threefold. (a) *Working results beat aspirational ones:* a tree ensemble trains in seconds on our data volume and produces a genuinely measured held-out-well number this cycle, whereas a sequence model needs far more labelled events than four wells reliably supply and risks overfitting. (b) *Interpretability:* feature importances map directly onto drilling physics a tool-pusher can act on (e.g. rising torque variance + falling ROP → stuck-pipe risk), which matters for crew trust and for thesis defence. (c) *It is the honest baseline a deep model must beat.* The rejected alternative — leading with an LSTM autoencoder for the headline — would have produced a more "impressive" architecture diagram but a weaker, possibly unmeasured claim. The LSTM is staged as future work, not a current result.

**3. Physics-informed features, not a raw-signal black box.**
Rather than feeding raw WOB/RPM/torque/standpipe-pressure channels straight into the model, we engineer features grounded in drilling mechanics — Mechanical Specific Energy (MSE), torque and ECD variability, hookload trend, gas-ratio features from C1-C5 chromatography for kick detection. Trade-off: feature engineering costs upfront analyst time and bakes in domain assumptions a pure deep network might otherwise learn. We accept this because, with only four-plus-one wells, hand-built physics features inject prior knowledge the data alone cannot supply, improve sample efficiency, and keep every prediction explainable in terms a petroleum engineer already trusts. A raw-signal black box was rejected as both data-hungry and unauditable for safety-critical alerts.

**4. Replay of historical data "as if live", not a true live feed.**
DrillGuard's streaming behaviour is demonstrated by replaying recorded Volve/Bilabri sequences through the inference path at their native cadence, so the model scores each timestep in temporal order exactly as it would on a rig. The rejected alternative — wiring a genuine live WITSML/rig feed — is infeasible and irrelevant for a capstone: we have no live rig, and a live feed would test plumbing, not the science. Replay gives identical algorithmic semantics (causal, no future leakage) while remaining fully reproducible for judges.

**5. The dashboard is a simulation / visualisation layer, declared as such.**
The React dashboard is a complete, polished UX prototype, but it is currently driven by simulated data (`mockData.ts`), not by live model output. We state this explicitly: it shows *how* alerts and risk scores would surface to a crew, not real-time predictions. The measured ML results in this submission come from the model run on real data, reported separately and labelled as measured; the dashboard is presented as the operator-facing concept pending wiring to the inference service. Conflating the two would violate §9.1, so we keep them clearly separated.

**6. Scope locked to the drilling (execution) phase only.**
EDIM stands for *Execution-phase* Drilling Intelligence Module by design. Our datasets contain MWD/LWD drilling-mechanics and gas data but **no** production data (no rates, PLT, or IPR). We therefore make no production-optimisation claims. Trade-off: a narrower headline; benefit: every claim is backed by data we actually hold, which is precisely the reliability the rubric rewards.
